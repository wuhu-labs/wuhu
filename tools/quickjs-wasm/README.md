# QuickJS for the web

`//tools/quickjs-wasm:quickjs` produces `emscripten-module.browser.mjs` (default export: `QuickJSRaw` module factory) and `emscripten-module.wasm`. The loader targets browsers and workers, with separate wasm, growing imported memory, and the synchronous embedding API. A web bundle can substitute these two files for `@jitl/quickjs-ng-wasmfile-release-sync@0.32.0` while keeping its `dist/ffi.mjs` and `quickjs-emscripten-core@0.32.0`.

The engine comes from the same patched `@quickjs` v0.15.1 archive as QuickJSKit. The wrapper, runtime exports and pre-JS templates come from quickjs-emscripten v0.32.0. That wrapper also requires upstream's Bellard-style module detector: `engine.ts` appends the additions from its pinned `0001-bellard-module-detection.patch` to the wasm translation unit. This leaves the existing native engine unchanged. The only wrapper patch changes its two ng header include paths for the non-amalgamated source tree.

BCR emsdk 5.0.3 is selected for C compilation only through `wasm_cc_binary`'s transition; existing native C and Swift targets retain their definitions and compilation flags. Its module dependencies affect the whole graph: rules_python rises from 1.8.0 to 1.8.4 and yq.bzl from 0.1.1 to 0.3.2. It also adds aspect_rules_js 2.9.2 and rules_nodejs 6.7.3, and globally registers Python 3.14 and Node 20.18 toolchains. The root lockfile records these resolutions.

`bazel test //tools/quickjs-wasm:smoke` runs in a real worker, loading the generated module through `quickjs-emscripten-core@0.32.0`'s `newQuickJSWASMModuleFromVariant` and the unchanged npm variant's 0.32.0 FFI. The loader fetches the adjacent wasm over loopback without `wasmBinary` or a custom file locator. The test checks every FFI export, script and automatically detected module evaluation, module namespace exports, a host promise driven by `executePendingJobs`, a module loader callback and interruption. Core, FFI and ffi-types archives are checksum-pinned; the test runs on the Linux and Mac check lanes.

## Script guest

`//tools/quickjs-wasm:script_guest` is the server's script engine: `guest.c` and the same engine linked as a standalone reactor (`guest.wasm`, no JS loader), which WuhuAddressables embeds and runs through WuweiWasm. Its only imports are `wuhu.receive`, `wuhu.send`, `wuhu.send_body` and `wuhu.expired` (QuickJS's interrupt handler); it exports `wuhu_enter`, `wuhu_entries`, its memory and `__stack_pointer`, since WuweiWasm refuses a module with an unexported mutable global. The target turns off emsdk's default `precise_long_double_printf` feature: its `libprintf_long_double` drags in `_tzset_js` and `_localtime_js`, which a standalone link cannot resolve.

Modules go through the guest's own loader. `wuhu:/<path>` names a space file and `./`/`../` resolve against the importing module's folder; any other `wuhu:<name>` is a built-in module the host hands over before the prelude (`wuhu:space`, `wuhu:space-core`, `wuhu:secret`, `wuhu:ai`, `wuhu:web_search`, `wuhu:session`, `wuhu:machine`), failing "not available yet" when it has not; `wuhu:host`, the host calls those modules share with today's server, imports only into another built-in module; and any other specifier fails. Before evaluating the main module, the guest compiles it in a throwaway context where every module not yet handed over compiles as an empty stub and is requested with a `{load}` frame; the host reads each one, hands it over with entry kind 3 (path, NUL, source), and enters the main module again once all have arrived, so a module graph loads in as many rounds as it is deep.

The guest's globals `__wuhu_send`, `__wuhu_decode`, `__wuhu_encode` and `__wuhu_seal` are the prelude's alone: it takes them and deletes them before any module evaluates, then seals its hooks into C with `__wuhu_seal({receive, fail, main, kernel, meta})`, so no host primitive stays reachable from the global object. `kernel` reaches only `wuhu:host`, as its `import.meta.kernel`; `meta` fills the main module's `import.meta` (`session`, and a terminal run's `args`) before it evaluates. The main module's evaluation promise and namespace go to `main` (a handler's main exports `handler` and `input`). Besides the JSON frames of entry kind 2, entry kind 4 hands over a frame, a NUL and raw bytes, which `receive` gets as an ArrayBuffer over the guest's own copy: a fetched body never passes through JSON. Going out, `__wuhu_send(frame, buffer)` hands the host a frame with raw bytes beside it through `wuhu.send_body`, as a fetch's request body. `__wuhu_decode` and `__wuhu_encode` convert between UTF-8 ArrayBuffers and strings for the prelude's `Response.text()` and friends, since QuickJS has no `TextDecoder`.
