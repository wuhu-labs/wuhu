# FetchTunnel

`Tunnel` turns one injected binary-message `TunnelTransport` into a scoped `FetchClient`. Its peer runs `Tunnel.serve` with a Fetch request-to-response closure (ServeTunnel adapts a Serve Handler). The acceptor calls Fetch; the dialer serves it. Neither endpoint contains application identities, routes, operation state, processes, retry policy or reconnect logic. A transport has one receive consumer and one sequential send producer. It must abort pending IO promptly when its synchronous `abort` closure is called.

The owner runs `run()` concurrently with client calls and awaits it during teardown. The endpoint is single-use; running it twice is `alreadyRunning`. Closing, aborting or corrupting a connection fails every admitted exchange on that connection. Construct a new endpoint for a new connection: it inherits no requests and replays nothing. Handler cancellation is cooperative; a handler which ignores cancellation can delay serving-task teardown, but occupies a bounded job slot until it exits. It cannot create unbounded abandoned jobs. Request-body collection is caller-owned, capped, and requires a cooperative Body producer; dispatch does not begin until collection is complete.

## Bounded exchanges

This version deliberately collects each request and response completely before sending it, and delivers a response only once its complete body is validated. It is not an unlimited streaming transport. Default limits are 32 active exchanges, 32 KiB JSON heads, 16 KiB body chunks and 1 MiB per body per direction. Configured limits are validated before running: the maximum head/chunk/abort payload plus its 10-byte prefix must fit the transport's maxMessageBytes (default 1 MiB for closure transports). The NIO adapter uses the minimum of inbound frame/message and outbound message caps; URLSession and ServeNIO expose their configured message cap. Known oversize bodies are refused before collection; unknown-length bodies are collected only up to the cap. Memory grows only with the configured stream, body, head and chunk caps (including transient collection/encoding copies), not with the number of exchanges over time. Receiving queues in live adapters have independent limits; no credit messages or replay buffers exist. Large streaming exchanges require a later protocol revision, not silently bypassing these caps.

Stream count includes body preparation, pending response delivery and handler work. Admission is immediate `capacityExceeded`, not an unbounded waiter queue. Handler jobs retain their own slots even after peer abort until they actually finish. Completed structured child tasks are continuously reclaimed through a bounded worker group. Outgoing frames round-robin between streams, one frame per turn; abort replaces that stream's unsent body. An early complete response discards any remaining unsent request frames before releasing the client's slot. There is no transport send task per chunk and no data-sized cancellation backlog. The transport's own send must cooperate with abort to release a stalled write.

## Wire contract

WebSockets negotiate exactly `wuhu-fetch-tunnel.v1`. Each binary WebSocket message carries exactly one tunnel frame: version byte `1`, type byte (`1` request head, `2` response head, `3` body chunk, `4` end, `5` abort), unsigned big-endian 64-bit nonzero stream id, then payload. Caps are not negotiated. Both peers must agree on compatible limits; lowering a receiver cap is a wire-breaking change for senders that use the larger cap. A message boundary is a frame boundary; there is no secondary length field. IDs are monotonically allocated after request-body preparation and never reused on a connection. Request heads arrive in increasing id order. A rejected opening head consumes its id even when its payload exceeds the head cap. A connection is unidirectional at the Fetch level, so body direction is implicit in the sender's role rather than a redundant field.

Heads are JSON objects with optional `method`, `url`, `status`, ordered `headers` pairs, `bodyPresent`, and exact collected `length`. Request heads carry method and absolute URL; response heads carry status (100 through 599). RequestHeaders already folds duplicates before transmission; response header pairs preserve duplicates. Body-derived Content-Type is added when no explicit header exists in either request-header store (sensitive or ordinary), and received Content-Type is restored into Body metadata. Sensitive request headers go onto the wire normally and are not logged. Header names and values are validated before construction. Missing-body requests are distinct from an explicitly empty body. A stream receives one head, zero or more nonempty capped chunks, and one empty-payload end matching the announced byte length. Abort payload is a stable TunnelError raw string (at most 128 bytes), never arbitrary handler error text.

Semantic errors (bad JSON/head, duplicate head, unknown/reused id, unexpected chunk/end, excess bytes, cap breach) abort only the offending stream with a typed error. Late traffic for a terminated id cannot revive it and receives an abort. Unknown aborts are ignored to prevent abort loops. Pending abort frames coalesce per id and have a separate stream-count-bounded control budget, so rejecting a new stream at full admission does not close healthy streams; exhausting that budget closes the connection rather than growing memory. Invalid version/type, zero id, truncated fixed framing or an end carrying payload is `corruptFraming` and aborts the connection. Handler failures are `handlerFailed`, not leaked implementation prose; arbitrary transport failures become `transportFailure`. Cancellation sends an abort for an admitted exchange, never a logical operation stop.
