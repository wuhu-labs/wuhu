# SpaceCore

## Database lifetime

`Space.inMemory()` opens an isolated SQLite memdb database with no scratch directory or database file. The memory opener uses SQLite’s in-memory rollback journal, while file-backed spaces retain WAL. Memory readers hold read transactions: a concurrent writer commit waits for them, up to the five-second busy timeout, then throws a SQLite busy error. Cancellation interrupts long queries and releases their read transaction. Sandbox readers attach the same memory database; files, tables, revisions, identities and queries follow the same implementation as `Space.open`. An unavailable memory VFS throws a SQLite database error, never opens a disk substitute. Memory databases copy a schema template without an identity, then run ordinary preparation. Both opening paths run the same ordered GRDB migrations and seed their own identity; existing file-backed data is retained. Migration 001 establishes the baseline for fresh and existing databases. Applied migrations are recorded transactionally in `grdb_migrations` and never run again. The once-only links reindex remains post-open maintenance because it reads external object storage and parses documents.


## Scope context

Nothing of scope context is staged here: the worker computes it after a tool call and appends it as an ordinary notice behind the tool result, and the notice entries carry the hash-to-first-path map that rebuilds generation-scoped dedupe state.


## Direct messages

`SessionStore.post` refuses every `.dmUser` post by a session, including a readable person–person DM addressed by id, and refuses either side posting into a person–session DM with `SessionStoreError.humanAgentDirectMessage`, whether opened with `.dm(with:)` or addressed by an existing conversation id, for either poster. The refusal text is exactly: "There is no DM between human and agent. If you want to notify a human that has talked in your conversation box, simply post that box, optionally specifying the reply target's message ID." The transaction writes no message, conversation, notification or queue input on refusal. Existing person–session DMs remain readable; there is no deletion or migration. People’s person–person DM posts, session–session DMs, boxes, group conversations, requests and reports are unchanged. Only an agent's box creates ordinary-message reply duty, never a person–session DM.

## Inferences

`inferences` is an induced, read-only SQL table available through query, observation and scripts with the same group visibility as `sessions`: the unqualified name reads the acting group, a group-qualified name reads a readable group, and the wildcard-qualified name includes `grp`. Opening an existing database creates the table and indexes idempotently; there is no backfill.

Each call has `id`, `session`, `at` (UTC start), `provider`, configured `model`, optional API-reported `served_model`, `effort`, `input`, `cache_read`, `cache_write`, `output`, `reasoning`, `outcome`, `error`, `duration_ms` and `ttft_ms`. `input` is uncached input; total input is `input + cache_read + cache_write`. `output` includes billed reasoning; `reasoning` is its reported subset or null when unavailable. Usage is null when a failed call reports none. Outcomes are `ok`, `networkError`, `httpError`, `timeout` and `cancelled`.

`Space.recordInference` inserts a call for an existing session and derives its group from that session. Observations wake on insertion. No lifecycle operation deletes inference rows: archive, compaction and Start over leave them intact.

## Archive support

`SessionStore.archiveSubtree(root)` returns records in descendant-before-parent order using the parent chain, not `created_by`. `closeRequestsForArchive(id)` posts one replay-safe final-kind message for every still-open request, including undrained input, and cancels its deadline subscription on the parent. The wording explicitly says the session was archived before reporting; it does not claim the requested work was completed. The store's `archive(id, grace:)` and `unarchive(id)` remain single-record persistence operations; the session service owns subtree orchestration and runtime interruption.

Archive reservations are shared by all `SessionStore` values of a space. `reserveForArchive(id, token:)` serializes reservation with session creation, `isReservedForArchive(id)` checks it without waiting for runtime work, and `releaseArchiveReservation(id, token:)` only releases the matching token. `hydrateForExecution` checks the main-owned archive reservation and loads the session in one SQLite read transaction, throwing `reservedForArchive` before decoding reserved data. Plain `hydrate` shares its loader without that admission check, so archive bookkeeping can inspect its reserved sessions. Creating a child below a reserved or archived parent fails with `parentUnavailableForCreation`; a separately created top-level agent remains allowed by this storage gate.

## Subscription progress

`SessionStore.fireSubscription` accepts a reschedule only when the new due time, serialized at the database's millisecond precision, is strictly later than the currently stored due time. An equal timestamp, backwards timestamp, absent due timestamp or sub-millisecond change that persists unchanged throws the session-observation SPI's `NonAdvancingSubscription` error, including the attempted and stored due times. A removed subscription row instead throws a stale-callback error. Both reject the fire before enqueueing its notification; the transaction leaves both queue and subscription progress untouched.

The session-observation SPI exposes both a fresh registration snapshot and its change stream, including observation callback identities. The firing registry reloads a fresh snapshot on task completion rather than relying on a due-time key change to wake it. Stored subscription schema and existing off-minute due rows are unchanged.

Request-deadline firing commits the parent queue notification, owner deadline notification and subscription retirement in one transaction. A failed write leaves all three effects uncommitted and the slot retryable; replay after retirement cannot append another owner notification.

`openRequest(stallSeconds:)` arms a `stall.<request>` slot on the parent whose payload is the request's stall clock: the last progress anchor, seconds paused, when the current wait began, and whether this streak has alerted. Without `stallSeconds` nothing is armed; a replayed request arms it again unless the request is closed, keeping an existing clock. `checkRequestStall(parent, subscriptionID:, now:, liveScripts:)` is one look in one transaction. It retires the slot when the request has a final or the task is no longer live. Otherwise it reads progress as the latest of: the end of an `ok` inference by the task or any descendant, any of their `run_progress_at` stamps, and the task's latest message in the request's DM. Newer progress moves the anchor, clears the paused time and re-arms the alert. Waits are read on the task alone: run state `tool` (since its `run_progress_at`), a script in `liveScripts`, the in-process executions the caller passes (since the anchor), a one-shot timer whose due time is still ahead (since it was armed), or an open request of its own (since it was posted). An armed observation and a cron timer are not waits. The time from the earliest wait's start, clamped to the anchor, to the first check that sees no wait is credited as paused, so a wait stops the clock from its real start without resetting it. While a timer holds the clock, the next check is no later than its due time. When the unpaused time since the anchor reaches the stall, one `requestStall` notification (deterministic id per request and anchor) is enqueued to the parent with the request, the last progress time and the task's visible state (`idle`, `errored`, `interrupted`, `unknown: inference open since T`, else `unknown`). A check that alerts or sees a wait schedules the next at most 60 seconds ahead while waiting, and one stall ahead after an alert. A final report and an archive cancel the slot; Start over keeps it without listing it as a subscription. No owner notification is written for stall alerts.

## Bounded transcript history

`SessionStore.transcriptHistory` reads a recent tail or one exclusive backward page in a database snapshot. Limits are 1 through 200. Older reads require the generation and before position together. The output carries ascending positioned entries, a backward boundary, authoritative extra-row exhaustion, the snapshot head and bounded origin attribution. Kernel reads select at most limit+1 pointer/payload rows and one indexed boundary assistant candidate; they do not hydrate the generation. The first leading tool-call result chooses the candidate via immutable chronological source-content row order, then verifies current-generation membership, preceding position and exact call ownership. A missing or excluded candidate yields no origin, never an older fallback. Generation heads do not participate in this lookup; compaction carries chronological source intervals without rewriting content. SQLite-managed VACUUM and VACUUM INTO preserve the relative source ordering used here. The legacy full snapshot is unchanged.

Bounded transcript observations read at most 201 forward entries. Generation changes and forward lag beyond 200 produce a reset-only page. The HTTP owner closes that stream so the client refreshes its recent tail.

The kernel history indexes are `session_contents_assistant_history(session_id)` and `session_pointers_by_content(session_id,generation,content_id,position)`. No existing table columns change. Opening an existing space builds missing indexes without changing source history. The first partial assistant index build evaluates existing source JSON synchronously; subsequent opens reuse it.

## Removed executor

A stored executor other than `kernel` decodes as `SessionExecutor.retired(kind:)`. Creation, hydrate-for-execution, resume, restart and unarchive throw `ExecutorUnavailableError` with description "executor no longer supported"; plain hydration returns an empty transcript, as do `transcript`, `transcriptHistory` and `transcriptSnapshot`; boot eligibility selects only `kernel` sessions. Queue input, identity, box, home, tags and children remain stored. Only Start over onto a supported executor clears the record; restart away opens a kernel generation and retains readable queued input and subscriptions. The removed executors' stores are dropped by migration 002.


Marking a session errored preserves corrupt transcript payloads; if transcript decoding fails, its error notification omits assistant text rather than rolling back the visible error state. Unreadable dates or executor/record payloads likewise cannot roll back the durable error update; an unreadable record receives an owner notification without transcript text.

The boot scan evaluates record decoding and parked-task eligibility per session. Its optional synchronous failure handler can collect an ID/error and return to skip only that session; the default handler throws. Database-wide read failures still throw. Corrupt settle history cannot roll back an otherwise valid session’s errored state; when parent failure notification cannot decode history, an owner error notification is emitted instead.

Start over alone writes an optional settle boundary (delivered queue tail and sent-message sequence) alongside the new head’s settle snapshot. Valid historical obligations carry over exactly as before, while undrained inputs stay queued for delivery into the new generation. If historical payload decoding or date parsing fails, Start over seeds an empty settle snapshot. Later store folds use the latest restart checkpoint and only subsequent queue/message events, even after compaction; prior payload rows remain unchanged. Heads without a restart boundary retain their prior serialized bytes. Older dev.88 decoders ignore the optional boundary and retain the head and explicit settle snapshot; their store-side full-history folds remain legacy behavior.

## Image fitting

`ImageFitting.fit` passes images whose measured dimensions and byte count already fit through byte-identically. Oversized images are decoded, resized to the model's long-edge and patch limits, and encoded to its byte limit. If fitting fails, the existing explicit `[image not sent: … this server could not scale it]` note is returned; no oversized fallback image is sent. Unmeasurable bytes within the byte budget retain the existing provider-pass-through behavior.

Apple platforms keep ImageIO, including its thumbnail EXIF orientation transform and PNG/JPEG encoding behavior. Linux decodes PNG and 8-bit JPEG with Bazel-pinned libpng and libjpeg-turbo; palette, grayscale, 16-bit and alpha PNG inputs normalize to RGBA8. JPEG EXIF and PNG eXIf orientations 1–8 are applied using bounds-checked TIFF views without copying chunk payloads. Bilinear interpolation weights colors by alpha. Linux tries the original format first (PNG preserves alpha), then JPEG qualities 85, 70, 55, 40 and 25; JPEG composites transparency on white. If bytes still do not fit, it retries at three-quarters of the long edge down to one pixel. Unlike ImageIO's resized-JPEG-to-PNG first attempt, Linux keeps JPEG as JPEG. Oversized other formats remain explicitly refused.

Image fitting refuses absurd header dimensions and uses checked arithmetic before invoking the model sizing calculation; `ImageLimits.fitted` computes its area ratio without overflowing integer multiplication. Linux decoding and C encoding reject images above 40 million pixels before allocating pixel buffers. Before libpng sees a PNG, a bounded chunk scan validates lengths and CRCs, requires a complete terminal IEND, and keeps only critical pixel chunks, transparency and fixed-size color/gamma chunks. Compressed text, ICC and other ancillary payloads never reach libpng and cannot expand into metadata allocations; eXIf orientation is applied separately in Swift. TurboJPEG confines libjpeg error longjmps to its C implementation, stops on truncated-input warnings, caps progressive scans at 100, and caps internal memory at 128 MiB. Bad input returns a fitting refusal rather than aborting the process.

## Guarded schema and historical inspection

`alterTable` accepts an optional VersionToken and allowDropColumns (the checked service requires the token and defaults the drop acknowledgement to false). Table liveness/kind is checked before the token, so missing, moved, deleted and non-table paths report notATable rather than a stale-token conflict. The liveness check, token check, omitted-column check, schema journal and DDL occur in one transaction; failure rolls everything back. Type changes remain refused. `tableSchema` reads the live header/token or a historical header/token, checking revision existence and node liveness in the same read transaction. Missing paths are notFound; non-table nodes are notATable. Historical tokens identify the historical node version, not an overwrite receipt. The checked SpaceToolContext boundary resolves caller paths, validates headers, and enforces group, session-home and protected-layer policy for HTTP and scripts; trusted core calls do not acquire a wallet identity. Template allocation/creation continues to use its existing atomic transaction.

## Guarded file creation and historical restoration

`writeFile(path, data, in, acting, ifMatch, createOnly)` resolves machine-note aliases and delegates to LiveFS's checked transaction. With createOnly, any current node conflicts before deduplication or replacement. A supplied version token is compared in that same transaction. The existing VFS write entry point keeps its optional-token semantics. `checkout` accepts optional ifMatch/createOnly checks against the current head inside the restoration transaction, before comparing content, minting a revision or altering file/table materialization. When both the historical node and live head are files with the same blob hash, checkout returns the live revision and current token without minting a revision, journaling history or emitting a mutation. Table checkouts always mint a revision, even when their restored rows are identical; restoring nonexistence keeps its existing deletion behavior. `history` supports an exclusive after revision and optional limit; the ordered join is a StructuredQueries selection and its limit is applied by the database.

`Space.fs(..., listingLimit:, listingByteLimit:)` optionally bounds listing hydration in the live-head, historical-version and machine-alias queries before Entry arrays are allocated. Non-nil limits must be positive. Cursor hydration stops when the running escaped-name size plus a conservative 256-byte metadata allowance per entry crosses listingByteLimit, throwing listingResultTooLarge. No full row array is hydrated first; historical listings convert each cursor node directly into an entry. The default remains unlimited for existing callers; script services select their cap plus lookahead and fixed hidden-root overhead.


Start over is an empty-summary compaction without a retained tail or pre-reads, using the same generation-head writer as compaction. It preserves armed observations (including callback identity and firing progress), one-shot and cron timers, and outgoing request deadlines; the new head snapshots those registrations. A malformed request-deadline registration with no fire date refuses the operation with `SessionStoreError.requestDeadlineWithoutFireDate`. Park reminders and pending compaction commands are removed. Error, hold, run/heartbeat/progress and retry state are cleared; the executor/model may change. Readable queued rows are neither marked delivered nor removed: a nonempty readable queue sets `has_work` and emits a fresh work signal, while subscriptions and the restart note alone remain inert. Session identity, conversations, prior generations, home files, children and open requests in either direction remain unchanged.


Start over validates each pending queue payload and its stored dates. Unreadable inputs are dropped from delivery and counted explicitly in the restart note; their original rows remain intact. If any input is unreadable, all readable pending rows move in FIFO order to IDs above the old queue head with their `input_id` and payload unchanged, and the tail/checkpoint advances past the unreadable originals in the same transaction. Re-enqueuing a moved input deduplicates against its unchanged identity. An all-unreadable queue remains inert and no longer prevents hydration or archive. Start over also clears `parkReminderCount` and `lastParkReminderAt` on retained open requests without changing their other fields or closing them.

## Human-only channels

`users` conversations are channels. They have people-only members and an optional title stored in `conversation_titles`; an absent row or NULL title preserves the members' names fallback. The additive side table opens on existing spaces without ALTER or backfill. Existing users rows are channels; historical session member rows confer no human access and no new session memberships are inserted.

`createConversation(members:title:in:)`, `addChannelMembers(_:people:as:)`, `removeChannelMembers(_:people:as:)` and `renameChannel(_:title:as:)` manage channels. Validation and each mutation are atomic. Adding or creating with a session member throws `ChannelError.sessionMember`; an empty person identity or blank non-null title is refused. Person members manage, read and post. Every session whose group reads the channel's home group manages, reads and posts without becoming a member. Other people cannot read or post, even in a group that reads the home group. An unread channel is indistinguishable from a missing conversation. The anonymous principal, including the `--dev` seat and `--public-read` reader, neither creates, reads nor manages channels; management returns the same unknown-conversation refusal as for a nonmember person. `conversations(reader:group:)` retains most-recent-active ordering by last message position descending.

Channel plain messages notify person members but enqueue no session unless addressed. Mention, reply-target and the attention window retain their existing behavior: after an agent answers, subsequent messages reach it only while both its message-count and time windows are open; the window closes at whichever bound passes first. Tasks do not join the attention window; a person's post never wakes a task. SQL conversation, member, message and channel-message notification views enforce the same channel readership, including qualified group and wildcard views. `readsFile(_:in:as:)` applies channel readership before group readability for file/attachment access, attachment-copy sources and parent directory listings. Removing a person from a channel also prevents copying its attachments into another conversation. `observeConversation(_:after:as:)` revalidates its principal in each snapshot, wakes on membership and group-read changes as well as messages, and terminates on loss of readership. Everything sidebars observe channels and the person's notification/read-marker unread state.

## Subscription handlers

`SubscriptionSlot.handler` is an optional space module path. The existing subscription payload stores its distinct arming incarnation, canonical JSON state (at most 16 KiB), last error, failure-streak flag, and current attempt token; legacy payloads decode with these fields absent. `ArmedSubscription.armedAt` is the original registration time. Re-arming an existing subscription ID is a crash retry and returns its persisted truth unchanged. Cancelling then re-arming mints a new handler incarnation and observation callback identity.

`beginSubscriptionHandler` checks the live owner and arming incarnation, suppresses an already-committed observation marker, records the attempt token and last-fired time, and returns the last successful state. A new attempt supersedes a previous in-flight attempt, including after a server restart. `finishSubscriptionHandler` checks both incarnation and attempt token in the same transaction as state persistence, marker advancement or timer rescheduling/retirement, and buffered wake enqueueing. A missing, cancelled, re-armed, archived, superseded or already-finished attempt returns false and changes nothing. Invalid or oversized JSON and non-advancing reschedules roll back the whole finish. Script filesystem/table/message effects remain immediate and at-least-once, not part of this transaction.

Success saves canonical state and clears the failure streak and error; its observation callback identity remains stable. Failure retains saved state, records the last error, and enqueues its notification only on the first failure of a streak. A cron or retry timer may advance its due time on failure without advancing state; an observation failure leaves its committed marker unchanged. Failure-streak suppression and state survive reopening the actual database. Last-fired time is recorded at each begin, including failures and interrupted executions. Start over and compaction preserve handlers and saved state. Archive preserves registrations for unarchive within grace, while atomically invalidating in-flight handler attempts. The registration observation tracks owner lifecycle and exposes an archived flag to cancel a running handler while its slot remains durable. `retireArchivedSubscription` atomically checks the current owner lifecycle and deletes the slot without a notification, so an unarchive cannot race between an archived check and deletion. Archived firings retire their slot without running the handler; slots not yet fired remain available after unarchive.

Silent handler retirement does not enqueue a notification or wake the owner to repair transcript-derived tool state. Current transcript/hydration reads supply a transient durable-registration projection in the same database snapshot; `registeredSubscriptions` atomically returns registration IDs and handler IDs, letting already-loaded runtimes refresh both transient projections before rendering, tool-state use and compaction. The compaction write applies the transaction's current registration set to both its persisted head snapshot and its returned transcript, preventing stale supplied snapshots or retained tool results from resurrecting retired public subscriptions. Historical transcript entries remain unchanged.


Handler-backed timers and observations are not guaranteed model wakes and do not suppress an open request's park backstop. Hydrated/current transcripts and returned compactions carry handler IDs as transient metadata alongside the durable registration-ID projection; plain timers and outgoing request deadlines retain their prior wake guarantee. Neither projection is stored in transcript Codable bytes or historical entries.

## Filesystem observation

`observeFS(glob:from:group:)` yields `FSCommit` values, each with a group, revision and nonempty matching event array. A commit is delivered atomically, in serialized database commit order, by a transaction-scoped buffer emitted after a successful commit while the writer is still held. The buffer is discarded on every rollback, including SQLite-initiated rollbacks that GRDB does not notify, and rebuilt on deferred external-blob retries. AsyncStream yields buffer without waiting for subscribers: a stalled consumer never blocks database writes. Cross-group moves yield a filtered commit in each affected group's stream. Unmatched revisions yield nothing. Recipient selection and filtering hold the subscriber mutex; delivery releases it before yielding so cancellation cleanup can remove a subscriber without a lock inversion. The serialized writer remains held through delivery, preserving commit order even when filesystem callers are concurrent.

With `from`, the subscription is registered before reading the journal snapshot. Replay groups the journal events by revision and filters each group by the glob; the live copy of every replayed revision through the snapshot ceiling is dropped whole. The `mutations` stream adapter flattens commits for legacy SSE and script consumers without changing their event shape.


## Trusted import support

`createTable` accepts an optional `RevisionAttribution`, recorded atomically with table creation just as `commitRows` records row-mutation attribution. `removeEmptyDirectory(path, in, acting)` checks directory kind and child absence in the same write transaction as its tombstone: a nonempty directory returns false without a revision; a missing/non-directory path throws its typed SpaceError. It refuses root/reserved paths. This trusted core primitive never recursively removes children and is used by import staging cleanup.

## Trusted composition and provisioning

`Space.open(file:identity:objects:log:)` optionally supplies the durable identity when provisioning a new database. A malformed identity throws `SpaceIdentityError.invalid` before creating the file; reopening an existing database with a different identity throws `SpaceIdentityError.mismatch` before schema preparation, without overwriting its identity. Omitting identity retains the existing entropy-generated id and reopen behavior. The supplied identity seeds only a database without an identity row.

`UserRecovery.add(space:name:admin:)` returns the created AccountRecord and uses the same first-admin and reserved-name policy as the offline folder command. `UserRecovery.invite(space:account:server:ttl:)` validates the account and uses the same single-use device enrollment token, deployment origin/fingerprint and output/note format as the offline folder command. These overloads permit trusted in-process administration without opening a second database instance or requiring the server to stop; they add no HTTP authorization bypass.

## Machine v2 persistence and diagnostics

`machineV2Store(group:key:problemsGroup:)` supplies the production OperationStore on new machine_v2_operations/channels/output tables; it never selects MemoryOperationStore or v1. The caller supplies a durable 256-bit symmetric key. Complete metadata/start inputs, pending writes and output payloads are AES-GCM encrypted with group/id authenticated context; input identity uses canonical keyed HMAC rather than a secret-bearing diagnostic summary. Wrong/lost keys are storeUnavailable, not plaintext recovery. Tables are additive; existing machine/exec rows keep their meaning.

Claims atomically reserve capacity, persist dispatch_consumed and unique `(grp, owner_scope, invocation_key)` before returning the one-use dispatch bit. Changed machine/start input is invocationConflict. Updates atomically persist encrypted payloads, cursors, accepted offsets, pending identical writes, evidence generations, snapshots, caller budget and stop intent, and roll back every field on throw. Admission is by bytes alone: the described machine's buffer, shared by every group's operations on it; there is no count cap per owner scope, group or machine. Each refusal names its bound (`bufferBytes`, `machineBufferBytes`, `pendingInputBytes`, `outputBytes`, `inputBytes`), and a reused operation id is `operationExists`. Retained output is one sealed row per chunk; a row that does not open or does not match its id is `storeUnavailable`, never skipped. Output rows an earlier server kept per channel are recognized by their id: the operation's output is dropped (`discard`) and its next write deletes them. Terminal/unknown receipts release live admission slots immediately; actual retained output and pending input stay counted against the machine buffer budget until taken or pruned. Encrypted receipts and unread output remain recoverable for seven days. Lazy five-minute maintenance prunes expired terminal receipts. Retained input/output use the same per-kind channel window capacities as OperationClient. The same store contract suite runs against SQLite, with reopen, concurrent claim, privacy and wrong-key examples.

`machineV2Recovery(group:key:)` returns owner+record pairs, including stop intent, for slice 5 to reconcile by ID and stop dead script owners; it never returns a new start permission. `registerMachineV2` validates the separately enrolled identity/group and records explicit membership. `recordMachineV2Presence` persists attached/detached/lost evidence, descriptions, local observation timestamps and reasons supplied by the coordinator; it does not derive presence from connection state or use peer timestamps. Slice 5 owns authenticated tunnel routing/coordinator startup and persistent key provisioning.

`machineV2TraceSink(group:problemsGroup:)` is the required synchronous durable trace closure passed to OperationClient. One row per request retains correlation/path, dispatch start, head duration, completion duration, status, error and incident pin; bodies, query strings, authorization and secrets are never stored. `machine_v2_trace` is an induced read-only projection with the same group-qualified/wildcard rules as sessions. Operational tables and encrypted payloads are not in the query catalog. Trace-store failures remain traceUnavailable at the client.

`recordMachineV2Problem` aggregates one `/wuhu/machine-v2-problems.table` row per invariant/category/stable error code and one durable incident receipt per incident+fingerprint. Repeated requests for the same incident do not increment occurrences; correlation linkage is retained in private incident receipts. Human reports use this same API/table. Terminal protocol faults (invalidResponse/invalidOffset/offsetExpired) detected by traces or store updates are recorded automatically. Expected sleeps, lease loss and deliberate unsupported inputs are not automatically counted as bugs. The required problemsGroup constructor argument identifies the one operational table across owner groups (slice 5 supplies shared); nil is a typed construction failure with no per-owner-group default. The lazily created editable table contains only first/last timestamps, occurrence count, fingerprint, invariant, error_code and status. No identities, correlations, paths, arguments or output are placed in public problem rows; incident/correlation linkage remains private server state.

Five-minute lazy maintenance expires ordinary traces after seven days and resolved incident receipts seven days after pin release; incident traces are pinned automatically, including later requests on that correlation. Setting their problem row status to fixed/verified/accepted releases pins on a subsequent trace write. `pinMachineV2Trace` explicitly pins/releases a correlation in its group. Missing/mismatched problems schema is a visible store failure, not a second log. No revisioned space file is written for ordinary polling traces.

## Compact command claims

`claimCompactRequest` checks the expected hydrated generation and live lifecycle, then materializes nonempty instructions once into the current transcript without deleting the standing command. No instructions means no transcript notification. The returned claim carries a unique request token and generation. Tokens live in the additive `session_command_tokens(session_id TEXT PRIMARY KEY, token TEXT NOT NULL)` table; existing command rows are unchanged, and a legacy pending row receives a token lazily when claimed. Old binaries ignore the new table and can still read, replace, take or restart commands. On re-upgrade, orphan token rows have no command or runtime-claim meaning; a new request replaces its token, and a legacy replacement is claimed from the current command row. Runtime claims are never persisted across process restarts. `append` and `writeCompaction` optionally acknowledge that claim in their write transaction: a different generation throws cancellation before writes, a replaced command stays pending, and failed writes roll back acknowledgement. Start over deletes standing commands and opens a fresh transcript, so a stale claim cannot resurrect instructions in it. Hydration returns the generation from the same database snapshot as the transcript.

## Machine v2 durable key validation

`machineV2HasEncryptedState` checks only the new v2 key-check/operation/channel/output tables. `validateMachineV2Key` authenticates the key check and every existing encrypted operation payload before dispatch can begin, and creates a key check only when absent. The authenticated check lives in its own `CREATE TABLE IF NOT EXISTS` table, so prior v2 rows and all v1 rows remain untouched. An absent external key with encrypted v2 state, a wrong key, or a malformed encrypted record is `storeUnavailable`; there is no plaintext or regenerated-key recovery. `machineV2RecoveryGroups` includes every group with stored operations, including removed groups, so startup cannot overlook an abandoned owner.

`machineV2DetachedMembers` reads confirmed, group-filtered detached presence at startup. The coordinator preserves that goodbye across server restarts and silence; only new valid description evidence reattaches it.

`consumeMachineV2JoinToken` checks machine-account membership in the additive v2 table inside the enrollment transaction before consuming a token or installing its key. Passing today's machine token leaves both token and key rows untouched. A machine move atomically updates its v2 membership/presence group while preserving immutable operation-owner groups. Existing enrollment behavior is unchanged.

Retained buffer reservations are counted across all caller groups sharing that machine; group and script admission remain group-scoped. Claims are serialized in the same store transaction, and cross-group capacity rejection reveals only `capacityExceeded`.

`machineV2PresenceEvidence(machine, group:)` returns only that owning group's persisted typed state, observation timestamp and optional reason. A registered member with no presence row is explicitly lost/neverAttached since its registration time; an unknown machine or different group returns nil. Missing-route routing can preserve confirmed detached/leftAt evidence across restart instead of inventing lost. Malformed stored state or timestamp throws `storeUnavailable`, never a synthesized state or date. Callers still authorize access before selecting the owning group.

Attached and detached observations record the fresh local answer/goodbye time. A lost transition preserves the previous observation timestamp, including a prior lost silence origin; a never-observed member uses its registration time. Consequently lost evidence supports stable silentSince diagnostics without synthesizing the time of a failed route lookup or changing the coordinator's monotonic lease accounting.

`addMachineV2(name:group:)` creates the machine account, separately named machine, owning-group v2 membership and one-hour single-use exec-machine join token in one serialized transaction. Every insert failure rolls back the complete enrollment, so retry can reuse the name; no half-created identity or token survives. Names follow the normal machine-name validation and global uniqueness rules.

`enrollMachineV2(name:group:pubkey:device:enrolledBy:)` is the token-less one-call form: one transaction creates account, machine, v2 membership, live exec-machine key (created by `enrolledBy`) and optional device link. It is idempotent per person: when the name is held by a v2 machine in the same group whose live exec-machine key is `pubkey` and was created by the same non-nil `enrolledBy`, it returns that machine and key without inserting anything (re-applying the device link); otherwise the held name is `machineNameTaken`. Consuming a machine account's join token writes a `join_token_receipts` row (token hash → pubkey, cascading with the key, pruned at the token's original expiry) in the claiming transaction, so a consumed machine token replayed with the same pubkey returns the same live key and any other pubkey is `JoinTokenRejected`; a person's token writes no receipt and stays strictly one-time.

## Durable model routes

`session_model_routes` and append-only `session_model_route_history` are additive `CREATE TABLE IF NOT EXISTS` domain tables. Existing tables/rows are unchanged; old direct sessions have no route and no backfill; their first execution establishes a concrete binding with nullable group/member. Group creation and Start over commit a legacy-readable concrete executor_config plus additive intent and `SessionModelRoute` with the session/generation/receipt transaction. Failed/busy operations cannot partially replace a pin. `modelRoute` reads it; `establishModelRoute` returns an already committed pin unchanged rather than repicking. Interrupt/resume and reopen preserve route epoch and placement evidence. Ordinary compaction can atomically replace a quota-aware group pin; a retained pin has no history churn. Start over replaces or clears the pin atomically without erasing previous decisions; switching to a direct target clears it. Rows include concrete provider/model, nullable group/member and phase `pinned` (groups) or `bound` (direct); payload carries requested group, effective effort, member, binding fingerprint, placement time/reason and all headroom evidence. FK deletion follows session deletion. The scoped readonly SQL projections `session_model_routes` and `session_model_route_history` follows `sessions` group visibility, including qualified/wildcard reads; it is not an editable space `.table`. Failure provenance lives in the existing route payload, not a new table.
## Cache warming scheduling

The additive `session_cache_warming` table stores only an agent's next deadline, configured interval, ping count and warming origin; its legacy `last_offer_tokens` column is unused. Warming claim and queue insertion are atomic and require a live, normally held, idle kernel agent not reserved for archive whose transcript, not counting pending warming notices, reaches the floor (`Transcript.reachesCacheWarmingFloor`); below the floor the claim fails without spending a ping or moving the deadline, and every enqueued notice offers compaction. The input is a context system notice with subscription id `cache-warming`; it creates no message/unread/notification record. The assistant commit atomically moves its deadline; a real-input inference also resets its counter. Warming-origin tool continuations preserve the count. Enqueue alone and silent handler firings do neither. Compaction preserves counters and origin. Start over deliberately clears all warming state. Ineligible pending warming notices are durably cancelled before an inference; empty cancelled context notices neither render nor create work. Restart recovery defers overdue deadlines by one interval and preserves counters. Rendering remains the ordinary append-only transcript path, without a persisted second copy of the prompt.

## Portable handoff storage

`writePortableHandoff` commits a projected generation only when the expected generation, source item sequence and replay binding still match. Rewritten contents require new IDs; unchanged message/receipt pointers retain their original identities and old contents are never mutated. New generation, bound head, work state and prompt revision commit atomically. The store treats the derived settle state on a hydrated initial generation head as equivalent to its persisted nil form; all other source changes are conflicts. Stale callers receive a typed `PortableHandoffConflict` without writes. This uses existing contents/pointers/generation storage; replay metadata is additive optional JSON, with no SQL schema change.

## Session run state

The induced `sessions` row carries `run_state` for kernel sessions, derived in the same transaction as the work flag whenever transcript items land: `tool` while the transcript has an unanswered tool call, `inference` while the model owes the next step (`has_work` with none pending, including just-drained input), and `no_run` otherwise. Interrupt, error, archive and Start over write `no_run`; resume re-derives it from the transcript. A forced compaction (the hard context limit, or a compact command) can start from a settled transcript, so the loop calls `markCompacting(active: true)`, which writes `inference` for a live, unheld, unerrored session, and `markCompacting(active: false)` on every exit, which re-derives the state from the stored transcript. The row is written only when the value changes: each change stamps `run_progress_at` (null for `no_run`) and moves `last_activity_at`. A pending tool call survives restart and its exec rejoins, so a session waiting in one keeps reading `tool`. `run_heartbeat_at` stays null.

## Session execution owner

SessionStore retains durable event operations, queue drain and compact claims. SessionTools.Main exposes these to execution as typed value operations on the directly conforming Hub; there is no in-process codec or store reference in the worker contract. Parent placement/admission still uses the store directly.

## Atomic route transitions and durable failure episodes

The held route payload optionally carries typed failure source (`upstream`/`credentialRefresh`), reason/code, first/latest failure times, frozen deadline, retry time and consecutive count. `updateModelRouteFailure` compares the expected epoch and updates only payload/phase (`waiting` for a refusing episode, otherwise `pinned`), without history churn. Start over clears it; success clears it without repinning. `modelProviderRefusing` supplies bounded member-scoped warming suppression (quota/auth account-wide, service failures model-specific). Only live normally held sessions with unexpired evidence count; a newer successful same-group/provider inference supersedes older evidence (same model for service failures), without changing the other session's persisted switching episode. No schema change or new table is required.

A `ModelRouteTransition` compares the held epoch and requires a changed group intent, member or concrete target with a new epoch, a bound account-neutral transcript, and no pending kernel calls; requested compaction targets may leave, join or change groups. A same-epoch transition is effort-only: everything but effort must match, and it updates only executor_config and the route payload, without history or transcript changes. Compaction/handoff commit its concrete executor_config, pin/history, portable contents/new generation, work state and prompt revision together. Handoff additionally checks expected generation and hydrated/raw source items. Failure at any write leaves the old pair intact; reopen after successful commit sees the new pair. Existing contents/receipts remain immutable, and obsolete epoch writes conflict. Last-resort history uses `lastResort:<typed cause>` while its legacy-readable payload uses the existing `compaction` reason plus optional `switchCause`.


## Machine value construction

`MachineRecord`, `ExecRecord`, `ExecClaim` and `ScriptExecOwner` expose value initializers for semantic owner adapters. Their store representation, authentication, exec replay receipts and database schema are unchanged; these initializers do not grant persistence or authorization authority and do not make store records Codable.

`SessionStore.bootSessions` includes settled live kernel sessions of either kind when durable settle state still contains an open incoming request. This lets the parent reconstruct park-reminder deadlines after restart without keeping execution actors loaded; settled sessions with no request remain absent from boot admission.

## Retired worker schema

The existing `session_worker_incarnations`, `execution_worker_owners`, `session_worker_assignments` and `worker_script_owners` table declarations remain unchanged. Runtime code neither reads nor writes them; removal is deferred to a separately authorized schema change. Script restart cleanup consumes only `script_execs`.

`Space.close()` finishes live filesystem subscriptions, cancels and drains the space-owned query, filesystem replay, and session observation workers, and explicitly closes every read connection and the writer. It attempts both readers and writer even if one fails, throws the first close failure, and is idempotent after success; database operations through the space and retained stores must finish before close and must not be used afterward. Hosts drain their services before closing the space, so no SQLite file handles or deferred close/checkpoint remain when shutdown returns. Observation admission after close returns a finished stream (or `TaskScopeClosed` for throwing observations); it does not start another worker.

Message handles and device names are resolved when queued inputs enter the transcript, in the drain transaction. Stored attribution survives hydration unchanged; directory renames affect only messages admitted afterwards.

Receipt writes accept a synchronous `onCommit` effect, invoked on the database writer after successful commit, before a subsequent database read can observe the result. Rollback does not invoke it. Tool-call exec results use the worker’s transcript append boundary instead of a separate receipt. The legacy `exec_jobs` table, when present, is retained empty and unused for rollback compatibility.

## Tool-call exec claims

`claimExec` atomically rejoins by caller and tool-call id, preserving the first claim’s optional opaque `toolSpec`. The nullable `machine_execs.tool_spec` column is added idempotently when an existing database opens; existing rows remain null. `setExecEndOwed` sets or clears the durable end-delivery obligation on an owning caller’s tool-call exec only. `owedExecs` (and `owedExecs(caller:)` for one session) returns tool-call execs with that obligation, terminal or live, ordered by start and id; `bootSessions` treats a session owed one as unparked. Existing detached job rows transfer their spec and owed flag into the exec registry, then are deleted from the retained legacy table so reopening cannot re-owe a delivered end. Request-stall clocks pause from the oldest live tool-call exec’s start rather than a separate job row; ordinary and script mints do not pause that clock.

`liveToolExecs(caller:)` selects that caller’s nonterminal tool-call records for main-owned archive relay cleanup. `forgetOwedExecs(caller:)` clears only that caller’s tool-call exec end obligations, live or terminal; archive bookkeeping uses it before revoking the worker token.

## Groups, settings and administration

A group may record an owner (`groups.personal_account`, unique): a person's own group, seeded with that person as its single member and its admin. It is hidden from discovery and from other people, and it keeps its content, sessions and machines. A new human gets that group and no membership in `shared`; existing shared memberships remain. A personal group is private: an incoming read edge into one is refused (`SpaceError.personalGroupPrivate`), migration 003 drops the legacy ones and rebuilds the read closure, and its files read only to its owner (any person) or to a session of that group. Acting in `shared` without a membership, and content-cookie admission there, stay deliberately until `shared` is open to every member.

Human admin authority is stored as direct account/group/role rows (`group_roles`, role `admin` today; no CHECK, so access roles extend it). A space admin holds `admin` in the settings group and administers every group but another person's own; the account admin flag derives only from that role. A personal role grants nothing over another group. Top-level agents still administer their own group, never the settings group, and no session takes the settings group as its home.

Migration 003 backfills personal-group owners and admin rows only for live accounts: a removed account keeps neither. It creates the hidden settings group and copies `shared`'s `models.json`, `model-groups.json`, `capabilities.json` and `machine-v2-upgrade.json` into it with new revisions, versions and heads over their existing blobs, then deletes them from `shared` as ordinary file deletes so the journal keeps their history. Settings are readable from every group and writable only by a space admin (or the dev seat). Instruction composition uses only the system files, the session's own group and its home; the space-wide layer, its toggle, its API/CLI and its persisted columns are gone.
