# OperationClient

`MachineOperations` is every machine operation of one `OperationStore`: admission, one driver per live operation, and machine descriptions. It takes an origin, a `FetchClient` (one dispatch per call: no automatic retry, redirect replay or fallback; start bodies are not replayable), the store, a clock, an id source, a `Tracer` (the bootstrapped one by default) and the `TunnelLanes` it shares with every other `MachineOperations` reaching the same tunnels. A server holds one per group store, all sharing one `TunnelLanes`.

## Contract

- `open(owner, machine:, start:, consumer:)` is idempotent by owner; `consumer` is the consumer's own JSON state, durable with the claim and never read here. The first opener claims the owner durably and sends the start once; every later opener, before or after a restart, gets the same operation. A different machine or start for the owner is `invocationConflict`. A fresh open returns once the machine took the start, or throws its typed refusal.
- An `Operation` handle offers `output(after:)` (retained chunks in arrival order across channels, nil once drained), `acknowledge` (the consumer is done through an offset; the chunk leaves retention), `write` (returns once the input is durable as pending; the driver delivers it at its offset), `stop(reason)` (durable intent, first reason wins), `abandon(reason, consumer:)` (stop and drop the output, retained and future, and replace the consumer state in the same write) and `verdict()`. Dropped output never advances the consumed cursors: they say only what the consumer acknowledged.
- `shutdown()` returns once no driver of the instance writes the store any more: in-flight writes finish, later ones fail, so an instance resumed over the same store is each record's only writer.
- `resume()` starts a driver for every live stored record, once, before callers can open; an owner still opening is skipped, so only its claim winner ever sends a start. A record the store cannot read is set aside instead and reported as such, alone. `setAside(operation)` does the same for a record its consumer cannot keep: the driver stops without another write, and the store ends the record. A claim whose start never left before a restart is never sent: its driver finds no operation on the machine and ends with a diagnostic.
- `describe`, `recentDescription` (the last description, while younger than a third of the machine's lease) and `forget` (drop what is cached about a machine that left the membership).
- `vfs(machine:op:owner:caller:)` and `search(machine:query:caller:)` are the normal tool adapters below.

## Admission

A start needs a fresh description: attached, accepting starts, listing the kind. A kind missing from the description and not named in `availability` is `unknownKind` (filesystem kinds say `agent too old, upgrade`); a gated or known-but-unlinked kind is sent, so the machine answers `kindUnavailable` or `permissionDenied`. Under a closed input schema (`additionalProperties: false`) a top-level field the schema does not declare is `kindUnavailable` with `reason: agentTooOld`, `started: false` and the sorted `inputs`. A start over `inputBytes` is `inputTooLarge`. With a tunnel stream count, an operation needs one control lane plus one lane per output channel next to two streams kept for describes; a start that does not fit is `capacityExceeded` with `reason: tunnelStreams`, `used`, `limit` and `requested`, before it is claimed. The lanes are counted in the shared `TunnelLanes`, from admission until the driver ends, across every instance (group) using the tunnel, so concurrent starts from any group cannot all take the same room; a resumed operation holds its lanes whether or not they fit. There is no count cap: the machine's `bufferBytes` bounds what it holds.

## The driver

The driver is the only code that talks to a machine about its operation. Its control lane sends the start (once), the stop, pending input and the terminal acknowledgement, and otherwise holds a state poll for at most the machine's `pollHoldMs` or a third of its lease, whichever is shorter, dropped as soon as a stop or input arrives. Each output channel has its own lane, which polls only while the channel's retained bytes leave room for a full poll within the channel window; past that the machine's window fills and the process blocks. Every answer is durable before the next request acknowledges it: a channel answer is one appended chunk, a state change one record save. A pre-verdict answer arriving after the verdict keeps only bytes that continue the channel.

The union of active driver persistence waits and in-process routing preparation does not consume the machine-silence budget, including while another lane is suspended. Each exchange has a real deadline: five seconds, or the hold plus five, cut to what is left of the lease since the machine last answered. One table (`disposition`) sorts every failure: transport, deadlines, cancellation, `machineUnavailable`, `supervisorUnavailable`, `capacityExceeded` and `storeUnavailable` are retried with backoff from 100 ms to 2 s; everything else, including codes this build does not know, ends the operation with the error as its diagnostic. A machine silent for a full lease ends it with `unknownOperation {reason: leaseSilence}`. Each exchange made under a current span is one `machine.exchange` client span under it, from the tracer `MachineOperations` was given, carrying only `machine.id`, `operation.id`, `machine.exchange.kind` (`describe`, `start`, `poll`, `stop`, `input`), `http.response.status_code`, `machine.exchange.head_ms` and `machine.exchange.elapsed_ms` on the injected clock, `wuhu.outcome` (`ok`, `errored`), and on failure `error.type` (the operation error code, `unknown` for one this build does not define) with error status; never paths, queries, bodies or messages. Its context goes out as the tracer's propagation headers. An exchange with no current span starts none. One machine failing cannot stall another's operations.

An operation is drained once its verdict is known and every output channel has committed its final offset; a verdict that arrives before the channels' final offsets does not drain it. Once drained and acknowledged by the consumer, the driver sends the terminal acknowledgement and the operation retires. The machine drops a settled operation, so `unknownOperation` after the terminal acknowledgement was sent is the retirement, not a diagnostic. Abandoning an operation already concluded by a diagnostic drops its retained output like any abandonment and still sends one stop, retried within the lease, so the process does not run on. A start the machine took whose answer the store could not keep is not a refusal: the operation runs, and the state polls bring the answer back.

## Store

`OperationStore` has `lookup`, atomic `claim` (create the owner's record, or return the existing one without dispatch permission), `read`, `live` (a record that cannot be read is listed with its damage, not thrown), `setAside` (end a live record: kept, no longer live, holding nothing), `save(record, appending:)` (state and cursors, plus at most one appended output chunk) and `trim(record, removing:)` (state, and delete acknowledged chunks). Output is retained per chunk until acknowledged; nothing rewrites a whole record's output. `MemoryOperationStore` is test persistence; the server's encrypted store is `MachineV2Store` in SpaceCore.

## Filesystem helpers

Internal typed `stat`, `list`, `readFile`, `writeFile`, `mkdir`, `remove` and `move` take machine, paths, a stable `OperationOwner` and an optional `StartRequest.Caller`. Each opens its operation, consumes and acknowledges its output, and returns the completed result; a failed verdict throws its typed error, a stopped one `operationEnded` with the reason. Any failure abandons the operation. `vfs` is the public MachineContract adapter and returns `VFSResult.error` only for filesystem, input and size outcomes; configuration, unavailable-machine, protocol, cancellation and deadline failures stay thrown `OperationError`s, never a v1 fallback. Tokens from stat/read/write interoperate. Read uses read.v1 with offset/length validation and the v1 8 MiB per-call bound. List streams metadata, then sorts within an 8 MiB encoded-record budget; a caller over a materialization bound stops the operation rather than returning a truncated success.

Write sends length plus SHA-256 in the start and streams the bytes as 64 KiB input chunks; an owner key with different bytes is `invocationConflict` even when path and length match.

`notFound` needs an explicit failed-lookup marker, never ENOENT alone: stat/remove/move sources (including ENOTDIR and EACCES) are `notFound`, missing destination parents for write/move stay `io`. Read/list establish metadata first; a failed open after a successful lookup is `io`.

`caller` is display-only, for the machine's audit, and not part of the invocation identity (`canonicalData`).

## Normal machine tool adapters

`search(machine:query:caller:)` runs one `SearchQuery` page through `search.v1` and decodes the `SearchPage` result; the agent's engine pages it, so cursors are FileSearch's, bound to the query. A failure carrying `details.search` comes back as that `SearchError`. A machine whose description lacks `search.v1` throws kindUnavailable with `reason:agentTooOld`, `started:false` and an `agent too old, upgrade` message before any start. There is no fallback.

Shutdown fences operation-store writes and drains cooperative claim, driver and cleanup lanes. Exchange waiters answer at their deadline or cancellation even if an adapter ignores it: transport workers stay named and retained by the machine-link scope until they actually return. Shutdown cancels that transport scope without waiting for non-cooperative adapters.
